Review the Student 4 feature architecture: interview scheduling, invitation, and coordination management.

This feature owns its own frontend (student-4-frontend), backend/API
(student-4-backend), and database (student-4-db) tiers. It reuses the shared auth
service (shared-api/shared-db) for identity (users and sessions) via an HttpOnly
session_token cookie, and never stores credentials or user profiles in its own
interview.db database.

Interviews are stored in student-4-db (`interviews` table) with application_id, staff user_id,
interview_datetime, link, and structured JSON assessment notes across 5 skill criteria.
It integrates cross-microservice with Student 3 (applications) to query applications and sync status
(Interview Requested/Scheduled), Student 2 (job postings), Student 1 (resumes), and shared-db (user names).
The backend renders HTML fragments for an HTMX frontend (calendar view, list view, schedule modal, and write-ups).

The AI interview assistant and smart scheduling capability (suggest optimal interview time slots from
staff availability and answer recruitment queries) is a self-contained AI-Mode integration owned by this
feature (routes/ai_mode.py, services/llm_client.py, prompts/), calling Ollama directly (llama3.1:8b) the
same way student-1/2/3/5 each own their own AI-Mode -- it does not depend on the shared ai-services/ai-mode placeholder.
