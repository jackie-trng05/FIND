After collecting a new evidence batch, consolidate it before committing:

```powershell
python shared/release2_reports.py consolidate
```

This removes redundant generated captures and superseded attempts, rewrites report links and compacts the audit. Verbose CI logs remain available through the captured GitHub run URLs instead of being duplicated here. Unresolved FAIL/PENDING records remain disclosed as compact summaries; consolidation never changes a result to PASS. Custom files not generated by the collector are left alone.

## Approved Production Fixes

Both backends return generic JSON 504 responses for upstream timeouts and 503 for transport failures, without exposing upstream exception details. Existing explicit finite read-timeout overrides are preserved; `None` uses the finite default.

Forced debugging was removed from all 17 Flask launchers, including the five student backends subsequently approved by the user. Duplicate frontend/database defaults and student-module fallback logging now use main's PR #66 implementation. The change does not make Flask's development server a production WSGI server.

Local regression transcripts are linked from the security and testing reports. They do not prove GitHub CI, individual commit-hook participation or cloud deployment. SQL construction, required container bindings, local Ollama placeholders and unrelated fallback behavior were not rewritten. The local stack was rebuilt from commit `d261e66` on 2026-10-17 before the current synthetic integration retest. Rebuild again after changing application source; old execution evidence does not validate newer images.

```powershell

```

The active hooks are main's 15 per-student Lab 11 pytest hooks, not a second reporting-specific hook set. They use pre-commit-managed Python environments, so VS Code's global Python does not need the scanner modules installed. Their `files` patterns select the affected student directories; `FIND_STUDENT_ID` applies only to the manual report commands below. Dependency hooks audit their isolated environment, not application manifests or container images.

Manual report scans use the active project environment and include the selected student plus shared code and local AI servers. Use your own student ID; with no ID, results are labelled `group`, not attributed to every teammate. Ruff uses security (`S`) rules, with pytest assertions excluded. Like Lab 11, the manual pip-audit scans installed packages in that environment. Install relevant application dependencies first. Each manual scan has a 180-second limit and records timeouts as failures.

## Local and Cloud Evidence

The reusable collector can populate machine-verifiable evidence from the repository root:

```powershell
python -m shared.release2_delivery regressions
python -m shared.release2_delivery hooks-preflight
python -m shared.release2_delivery local-ai
python -m shared.release2_delivery contributions
```

`regressions` runs shared tests and all five student unit suites in isolated processes. `hooks-preflight` captures all 15 active hook results without invoking a commit or claiming student participation. `local-ai` requires the running Docker stack, Ollama, RAG and Multi-Agent servers. It creates synthetic applicant/staff accounts and a readable synthetic PDF, performs authenticated backend CRUD and all four AI integrations per feature, then removes fixture records and logs out. Two synthetic accounts remain per run because there is no supported user-delete API. Never run this against a production database.

AI checks validate populated, feature-specific output, not factual accuracy. MCP requires source citations; RAG requires nonempty source-linked retrieval results, not a generated-answer quality test. Multi-Agent requires three successful agents, nonempty evidence and no detected model fallback. Its request must name the actual interview ID for Student 4. It never submits a human decision. The retained retest uses the corrected interview scope and uploaded profile resume. Superseded fixture failures and the corrected hook-ID matcher attempt were removed during consolidation, not reclassified as passing tests.

Current local reports therefore distinguish passing backend checks from pending full frontend interaction and human review. Browser-shell evidence only proves the pages rendered. Existing human workflow records for Students 2-5 have audited decisions and evidence; Student 1's decision still lacks `evidence_used`. Do not fill that field without the actual person's assessment.

`contributions` captures the latest twelve actual commits touching each feature and creates missing input templates without overwriting them. These are unconfirmed drafts, not student-to-author identity mappings. Complete each student's contribution input from confirmed responsibilities and genuine commit links, then import it as described below.

```powershell
python shared/release2_reports.py snapshot
python shared/release2_reports.py workflow
python shared/release2_reports.py template --kind local --student student-1
python shared/release2_reports.py template --kind cloud --student student-1
```

`snapshot` is read-only: it records Docker Compose service state without restarting anything. `workflow` reads the existing Multi-Agent JSONL files without modifying them; its privacy-minimised snapshot records statuses, counts and human-decision linkage. It does not prove frontend execution. Current Planner and Worker execution is concurrent; review this against the brief's plan-driven sequence rather than assuming structural presence proves compliance.

Complete the generated `inputs/student-1-local.json` and `inputs/student-1-cloud.json` using real observations. Repeat for all five students. Required check keys are supplied in each template. Every check needs `PASS`, `FAIL` or `PENDING` and a specific evidence reference. Include:

- Named reviewer, actual UTC timestamp, feature and frontend URL.
- Captured terminal/service logs, browser evidence and expected/actual CRUD results with record IDs (redact personal data).
- Local: AI-Mode, MCP, RAG, Multi-Agent and human review through the frontend/backend path; start each non-containerised service in a separate terminal and retain its transcript.
- Cloud: Azure or AWS, resources, successful `cloud-deployment.yml` URL/logs, frontend/API/database/CRUD and persistence validation; verify all four AI services are disabled by default.
- Limitations, failures, corrections and retest evidence. A health check alone is insufficient.

Store sanitised supporting files under `evidence/` and reference them in the JSON, then import:

```powershell
python shared/release2_reports.py record --kind local --student student-1 --source docs/release-2/reports/inputs/student-1-local.json
python shared/release2_reports.py record --kind cloud --student student-1 --source docs/release-2/reports/inputs/student-1-cloud.json
```

Template commands never overwrite an existing input. Refresh regenerates reports but preserves input files and timestamped evidence. Importing a human record validates its shape, not the truth of a screenshot, URL or observation. The reviewer is responsible for that verification. Deployment infrastructure and deployment workflow implementation are separate work; this tool cannot deploy an application or manufacture their execution logs.

## Agentic Reviews

With Ollama running and the configured implementation/reviewer models available:

```powershell
python shared/release2_reports.py review --mode multi_agent
python shared/release2_reports.py review --mode pre_test
python shared/release2_reports.py review --mode cicd_test
python shared/release2_reports.py review --mode deployment
```

The same evidence-capture path is used by the interactive agentic-loop Release 2 menu. Reports and exact OBSERVE / IMPLEMENTATION / REVIEW transcripts are saved automatically. Consolidation retains successful review transcripts; unresolved failed reviews retain their status and execution header instead of bulky unsuccessful responses. Reviews consume captured evidence or linked structured summaries, not just filenames. With no execution evidence, a review is explicitly a gap review, never proof of execution. Missing students and pending checks must be flagged. COMPLETE means two models returned assessment sections and required evidence labels, not that the application passed or the human approved it. This is not a factual-accuracy guarantee: inspect both model outputs and reject unsupported claims. Rerun after changing inputs; stale reviews are listed in the completion checklist. Excessive input is rejected rather than silently truncated. Use the installed Ollama models; do not download additional models without approval.
